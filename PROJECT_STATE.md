# FO’X — состояние проекта

Актуально на 15 сентября 2026 года.

## Архитектура

- FO’X — Telegram Mini App, опубликованная из корневого `index.html` через GitHub Pages.
- Tatooine — отдельная Mini App в `tatooine/`, отдельный Telegram-бот.
- FO’X и Tatooine используют общий Scanner/Cash Apps Script для OCR, части Telegram-интеграций, графиков сотрудников, RBAC и связанных служебных операций.
- Банкетный модуль использует цепочку Mini App → Cloudinary → backend → Google Sheets.
- Gemini вызывается только из Apps Script; API-ключи, Telegram Bot Token и закрытые идентификаторы должны храниться в Script Properties.
- Для новых модулей сохраняется принцип: frontend отвечает за UI и подготовку данных, backend — за авторизацию и бизнес-логику, Google Sheets/БД — за бизнес-данные, внешние мессенджеры не являются источником истины.

Подробнее: `ARCHITECTURE.md`, `FOX_MEMORY.md` и документы в `docs/`.

## Production / ручные deployment, которые отличаются от `main`

### Банкетный Telegram topic filter

Пользователь вручную развернул существующий Scanner/Cash Web App как Apps Script version 66 с описанием `v9.11.1 BANQUET TELEGRAM FOX TOPIC FILTER`.

Цель этой ручной production-правки:

- фильтровать Telegram не только по `chat_id`, но и по `message_thread_id` темы FO’X;
- игнорировать `Tatooine` и `Общие вопросы` внутри той же Telegram forum-группы;
- сохранять `TELEGRAM_BANQUET_SOURCE_CHAT_ID` и `TELEGRAM_BANQUET_SOURCE_THREAD_ID`.

Важно: эта `v9.11.1` пока не считается синхронизированной с `main`, пока её точный код не сравнен и не закоммичен в репозиторий.

Текущий blocker автоимпорта: бот был добавлен в Telegram-группу с включённым Privacy Mode. Privacy Mode отключён через BotFather, но у пользователя нет прав удалить и заново добавить бота в группу. Для продолжения нужен администратор Telegram-группы, который пере-добавит бота; после этого нужно отправить новую Estimates Guru ссылку в тему FO’X и снова выполнить `foxBanquetsCaptureTelegramSourceChat()`.

## Текущие направления работы

### 1. 🔧 Ремонт / задачи хаус-мастеру — проектирование MVP

Согласован базовый принцип UX: сотрудник не заполняет форму, а в чате просто рассказывает, что сломалось. Бот должен сам извлекать известные данные и задавать только недостающие вопросы.

Целевой MVP:

- новый раздел FO’X с рабочим названием `🔧 Ремонт`;
- чат-диалог вместо анкеты;
- обязательные данные: описание, ресторан, зона, фото, срочность;
- ресторан FO’X определяется автоматически из контекста приложения, если возможно;
- зоны на первом этапе: Бар / Кухня / Зал / Бэк, но модель должна быть расширяемой;
- фото — только выбор из галереи, без прямого открытия камеры;
- срочность: Обычная / Срочная / Критичная; AI может предлагать, пользователь подтверждает;
- перед созданием тикета показывается краткая сводка с `Отправить / Изменить`;
- source of truth — backend FO’X / БД, не Пачка;
- Пачка используется для доставки и обработки задачи хаус-мастером;
- статусы MVP: `Новая → В работе → Ожидает → Выполнена`;
- сразу сохраняются данные для будущей аналитики: время реакции, время выполнения, ресторан, зона, тип проблемы, исполнитель, повторяемость.

Предлагаемая техническая база: переиспользовать существующие Telegram auth, `foxCurrentUser`, Gemini backend и direct Cloudinary upload; тикеты и event history хранить отдельно от stock/cash-таблиц. Для обратного webhook Пачка → FO’X требуется отдельная проверка безопасной схемы подписи/ingress.

Код Repair MVP ещё не начинался.

### 2. Автоимпорт банкетов

Базовая backend-логика уже находится в `main`, но живой end-to-end production сценарий ещё не подтверждён из-за Telegram bot/topic настройки.

Критерий готовности остаётся:

`новая Estimates Guru ссылка в теме FO’X → webhook → Gemini → создание/обновление банкета → обновление резерва → банкет виден в FO’X без ручного запуска функций`.

### 3. Сканер документов / PDF

Последний `main` содержит `v15.16.4`. Ранее пользователь воспроизводил зависание scanner polling и затем `Load failed` при подготовке PDF; эти места были последовательно исправлены в `v15.16.2–v15.16.4`.

Живой пользовательский тест именно `v15.16.4` после последнего исправления в этом проектном контексте не зафиксирован как подтверждённо успешный. Не считать сканер окончательно стабилизированным без повторного теста.

### 4. Кассовый отчёт

Основная текущая UI-проблема — клавиатура внутри Telegram Mini App. Candidate fix находится в отдельной ветке и ждёт merge/release/live test.

OCR и финансовая логика кассового отчёта не должны меняться в рамках keyboard fix.

### 5. Календарь / сотрудники / RBAC

FO’X уже использует `foxCurrentUser`, роли/permissions и служебную запись пользователя по проверенному Telegram ID. Графики сотрудников и доступы работают через общий Scanner/Cash backend.

При расширении на несколько ресторанов нужно отдельно добавить location/restaurant scope: текущая модель ролей не является полноценной multi-restaurant permission model.

## Известные проблемы и риски

- Scanner/PDF `v15.16.4` требует живого подтверждения после последнего исправления `Load failed`.
- Keyboard fix `v15.16.5` пока только candidate и не находится в `main`.
- Ручной production backend `v9.11.1` topic filter не синхронизирован с точным исходником `main`; перед будущим backend-релизом нужен compare.
- Автоимпорт банкетов заблокирован до пере-добавления FO’X-бота администратором Telegram-группы после отключения Privacy Mode.
- Banquet multi-photo/schema migration остаётся candidate и не должна применяться setup-функциями без отдельного подтверждения.
- Фактические Spreadsheet IDs, текущие формулы и значения Script Properties нельзя выводить из документации — перед backend/schema-изменениями требуется проверка production.
- `PROJECT_STATE.md` ранее отставал от фактического `main`; с этого обновления состояние репозитория и ручные production-deployment фиксируются отдельно.

## Что не делать без отдельного подтверждения

- Не запускать `setupBanquetsBackend()` и другие setup-функции.
- Не менять production Google Sheets схему вслепую.
- Не публиковать секреты/Script Properties в Git.
- Не считать branch candidate production-релизом без merge + deployment + пользовательского теста.
- Не использовать Пачку как базу тикетов Repair; Пачка только внешний интерфейс доставки/обработки.

## Текущая задача

Спроектирован MVP системы технических задач хаус-мастеру: чат FO’X → структурированный Repair Ticket → backend source of truth → Пачка → обратная синхронизация статусов/комментариев.

Следующий шаг по этому направлению — после подтверждения архитектуры начать реализацию в отдельной ветке, сначала с backend/data model и AI draft, затем с chat UI и интеграцией Пачки.
