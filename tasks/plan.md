# План: надёжный календарь и доступ сотрудников FO’X

## Цель

Сделать календарь одинаково надёжным на всех устройствах, затем дать каждому
сотруднику безопасный доступ только к своим сменам через проверенный Telegram ID.

## Решения

- Банкеты физически остаются в существующей production-таблице, но чтение и
  запись идут через защищённый FO’X Stock backend. Старый Banquets Web App
  после миграции не принимает ни список, ни операции записи.
- Роли и permissions переиспользуют существующий Tatooine user store, а не
  создают второй набор аккаунтов.
- График хранит `employeeId` как источник истины. Сравнение имён остаётся
  только временной совместимостью для ранее сохранённых строк.
- Неактивный или непроверенный Telegram-пользователь получает безопасный
  минимум `employee`; он не увидит смены другого человека по подставленному имени.

## Этапы

1. **Надёжная общая база.** Читать и изменять банкеты через подтверждённый
   FO’X backend: ограниченные повторные попытки, явная ошибка, локальный
   fallback только как отображаемая последняя копия. Не отдавать банкетные
   данные из публичного legacy Web App.
2. **RBAC-ядро FO’X.** Добавить permissions для графика и банкетов, безопасный
   current-user DTO, server-side checks и экран назначения роли для superadmin.
3. **Связь сотрудник ↔ Telegram.** Добавить явное управление привязкой к
   существующей записи сотрудника; `employeeId` перестаёт зависеть от порядка
   имени в Telegram. Сделать аудит изменений.
4. **Контур качества графика.** OCR preview показывает число распознанных и
   непривязанных сотрудников/смен; admin может исправить привязку до
   подтверждения. Активируется только явно подтверждённый график.

## Риски

| Риск | Митигирование |
| --- | --- |
| Нестабильный Banquets Web App | Проверить существующий deployment и сохранить URL; не маскировать ошибку пустым списком. |
| Подмена имени в Telegram | Идентификация и права — только по проверенному Telegram `initData` и user ID. |
| Ошибка привязки сотрудника | Ручная административная привязка и audit log; имя не становится security boundary. |
| Ошибка OCR | Непривязанные/подозрительные строки видны до сохранения, а не скрываются. |

## Контрольные точки

- После этапа 1: календарь либо показывает общую базу, либо понятное
  повторяемое состояние без потери локальной последней копии.
- После этапов 2–3: сотрудник видит только себя, manager/admin — состав смен,
  superadmin может назначать доступы; backend тесты запрещают обход через URL.
- После этапа 4: график можно проверить и связать до активации; tests/lint и
  ручной Telegram smoke-test проходят.
