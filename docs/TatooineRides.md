# Tatooine — развоз сотрудников, этап 1

## Модель

Постоянные данные хранятся в существующем листе `Tatooine_Пользователи`: `Адрес развоза`, `Широта развоза`, `Долгота развоза`. Менеджер может выбрать адрес из подсказок Geoapify: выбранный вариант сохраняет проверенный текст и координаты. Ручной ввод по-прежнему допустим, но не создаёт фиктивных координат.

Подсказки запрашиваются только после открытия менеджером диалога адреса и ввода минимум трёх символов; запрос дебаунсирован. Backend повторно проверяет `rides.manage_addresses`, передаёт Geoapify только поисковую строку и не отдаёт API-ключ клиенту. Ключ хранится в Script Property `GEOAPIFY_API_KEY`.

Заявка на конкретный день хранится отдельно в `Tatooine_ЗаявкиРазвоза`. Ключ уникальности — `Employee ID + Дата развоза`; запись с `Развоз нужен = YES` является единственным активным состоянием. Отсутствие записи и запись `NO` означают, что сотрудник не едет.

Дата развоза — текущая календарная дата в часовом поясе Apps Script. В Tatooine нет модели смен, поэтому `shiftId` пока намеренно не создаётся.

## Доступ

- `rides.view_self` и `rides.submit_self`: сотрудник видит только свой адрес и включает/отменяет собственный развоз.
- `rides.view_all`: менеджерский список активных заявок на сегодня.
- `rides.override`: добавить сотрудника в развоз или убрать его.
- `rides.manage_addresses`: посмотреть и изменить адреса сотрудников.

Все операции проверяются в Apps Script после проверки Telegram initData. Self-action не принимает `employeeId` от frontend. Адреса других сотрудников не возвращаются self-endpoint'ом.

## Настройка и TODO

Листы создаются лениво при первом входе в раздел «Развоз»; существующий лист пользователей расширяется только тремя колонками справа, без сдвига данных. Не запускать setup-функции ради этого модуля.

Опциональный Script Property `TATOOINE_RIDE_REQUEST_DEADLINE` в формате `HH:MM` закрывает self-service заявки после дедлайна. Менеджерский override остаётся доступен.
